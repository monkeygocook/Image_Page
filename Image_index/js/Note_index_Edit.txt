## แถบคิว + แถบเวลา: คำอธิบายสำหรับทีม และโค้ดฝั่ง Frontend

ผมแบ่งเป็น 3 ส่วน:
1. **คำอธิบายสำหรับทีม** คัดลอกไปส่งได้เลย
2. **งาน Frontend ของเรา** คือโค้ดแถบคิว
3. **คำขอถึงปั้น** คือข้อมูลที่ backend ต้องส่งมาให้

---

# ส่วนที่ 1: คำอธิบายสำหรับทีม

## ⏱️ แถบคิวและแถบเวลาบนปุ่มสีส้ม ทำงานอย่างไร

### ภาพรวม: แบ่งเป็น 2 ช่วง

```
กดปุ่มส้ม ──▶ [ช่วงที่ 1: รอคิว] ──▶ [ช่วงที่ 2: ประมวลผล] ──▶ ได้ภาพ ปุ่มกลับเป็นข้อความเดิม
              "อยู่คิวที่ 3 จาก 5"     "เหลือ ~12 วิ · 0:03"
              ข้อมูลมาจาก backend     ประมาณจากเวลาที่ใช้จริง
```

| ช่วง | ปุ่มแสดงอะไร | ข้อมูลมาจากไหน |
|---|---|---|
| รอคิว | `อยู่คิวที่ 3 จาก 5 · รอมาแล้ว 0:08` และแถบวิ่งไปมา | backend ส่งลำดับคิวมาให้ (frontend ถามทุก 1 วินาที) |
| ประมวลผล | `เหลือ ~12 วิ · 0:03` และแถบขยายไปทางขวา | เวลาที่ใช้ประมวลผลจริงในรอบก่อน ๆ |
| เสร็จ | ปุ่มกลับเป็นข้อความเดิม เช่น "Color Grade" | ไม่มี |

### เวลาที่แสดงมาจากข้อมูลจริง ไม่ได้สุ่มขึ้นมา

1. **วัดเวลาจริงทุกครั้ง:** ทุกครั้งที่ประมวลผลสำเร็จ ระบบจะจับเวลาตั้งแต่**ได้เริ่มประมวลผลจริง**จนถึงได้ภาพกลับมา แล้วบันทึกแยกตามเครื่องมือ (`genimage`, `back`, `icon`, `tone`, `blur`)
2. **ใช้ค่ามัธยฐานของ 5 ครั้งล่าสุด:** ใช้มัธยฐานแทนค่าเฉลี่ย เพราะถ้ามีครั้งไหนช้าผิดปกติครั้งเดียว ค่าประมาณจะไม่เพี้ยนตาม
3. **ถ้า backend มีค่าเฉลี่ยจากเซิร์ฟเวอร์ จะใช้ค่านั้นก่อน:** ค่านี้วัดจากการใช้งานของผู้ใช้ทุกคน จึงแม่นกว่าสถิติในเบราว์เซอร์เครื่องเดียว
4. **ไม่นับเวลารอคิวรวมเข้าไป:** ถ้านับรวม ช่วงที่คิวยาวจะทำให้ค่าประมาณสูงเกินจริงไปตลอด

> **ข้อจำกัดที่ต้องบอกตรง ๆ:** ก่อนจะมีสถิติจริงสักครั้ง ระบบจะใช้ค่าเริ่มต้น (`genimage` 90 วิ, `back` 15 วิ, ที่เหลือ 5–8 วิ) ซึ่ง**เป็นค่าที่ตั้งไว้เอง ยังไม่ใช่ค่าที่วัดมา** เมื่อใช้งานจริงไป 1 ครั้ง ค่าเหล่านี้จะถูกแทนที่ด้วยเวลาที่วัดได้ ถ้าแก้วส่งเวลาที่วัดจากเครื่องเดโมมาให้ (`AI-14`) เราก็จะใช้ค่าจริงได้ตั้งแต่ครั้งแรก

### ข้อความบนปุ่มในแต่ละสถานการณ์

| สถานการณ์ | ข้อความ |
|---|---|
| ส่งคำขอแล้ว แต่ backend ยังไม่ตอบข้อมูลคิว | `กำลังเข้าคิว... · 0:01` |
| อยู่ในคิว | `อยู่คิวที่ 3 จาก 5 · รอมาแล้ว 0:08` |
| ถึงคิวแล้ว และเหลือเวลาตั้งแต่ 90 วินาทีขึ้นไป | `เหลือ ~2 นาที · 0:05` |
| เหลือ 1–89 วินาที | `เหลือ ~12 วิ · 0:03` |
| เกินเวลาที่ประมาณไว้ไม่ถึง 3 วินาที | `ใกล้เสร็จแล้ว...` |
| เกินเวลาที่ประมาณไว้ไปมาก | `ใช้เวลานานกว่าปกติ...` (แถบจะหยุดที่ 99% และไม่เต็มก่อนได้ผลจริง) |

### สิ่งที่แถบนี้ไม่ได้ทำ
- **ไม่ได้แสดงเปอร์เซ็นต์ความคืบหน้าจริงของ AI:** แถบเป็นค่า*ประมาณ*จากสถิติ ไม่ได้รู้ว่า AI ทำถึง step ไหนแล้ว
- **ถ้า backend ยังไม่เปิดระบบคิว:** จะข้ามช่วงรอคิวไป แล้วแสดงแถบเวลาอย่างเดียว เหมือนเวอร์ชันก่อนหน้า หน้าเว็บจึงไม่พัง

# ส่วนที่ 2: งาน Frontend (ของเรา)

### ⚠️ ขอแย้ง 1 จุดก่อนเริ่ม: ตอนนี้ frontend ยังรู้ไม่ได้ว่าคำขอไหนเป็นของใคร

ตอนนี้ frontend ส่งคำขอไปครั้งเดียว แล้วรอจนได้ภาพกลับมา ระหว่างรอ frontend จึงถาม backend ไม่ได้ว่า "คำขอ*นี้*อยู่คิวที่เท่าไหร่" เพราะไม่มีรหัสอ้างอิงร่วมกัน

**วิธีแก้ที่ต้องแก้น้อยที่สุด:** ตอนกดปุ่ม frontend จะสร้างรหัส `X-Request-ID` แล้วแนบไปกับคำขอ จากนั้นใช้รหัสเดียวกันถามสถานะคิวทุก 1 วินาที วิธีนี้**ไม่ต้องเปลี่ยน endpoint เดิม** ของทั้ง 5 เครื่องมือเลย

---

### `[ETA-78]` แทนที่ `Image_index/js/eta.js` ทั้งไฟล์

**สวิตช์ `QUEUE_ENABLED`:** ตอนนี้ตั้งไว้เป็น `false` เพราะ backend ยังไม่มี endpoint คิว ถ้าเปิดไว้ตั้งแต่ตอนนี้ ปุ่มจะขึ้น "กำลังเข้าคิว..." อยู่ 3 วินาทีทุกครั้งโดยไม่มีคิวจริง เมื่อปั้นแจ้งว่าพร้อมแล้ว ค่อยเปลี่ยนเป็น `true`

### `[ETA-79]` เพิ่มต่อท้าย `style.css` (ต่อจาก ETA-77)

```css
/* ---------- ช่วงรอคิว: แถบวิ่งไปมา ---------- */
#submitBtn.eta-queued .eta-btn-bar {
    width: 30% !important;
    transition: none;
    animation: eta-queue-slide 1.4s ease-in-out infinite;
}
@keyframes eta-queue-slide {
    from { left: -30%; }
    to   { left: 100%; }
}
```

### `[FE-79]` `api.js`: แนบรหัสคำขอไปด้วย (เพิ่ม 2 จุด)

ใน `Api.image.process` ให้เพิ่ม `requestId` ลงในค่าที่รับเข้ามา แล้วใส่ header ตรงที่สร้าง `headers`:

```js
// 1) เพิ่ม requestId ในวงเล็บที่รับค่า (ชื่ออื่น ๆ ให้คงไว้ตามเดิม)
process({ tab, cfg, file, /* ...ของเดิม... */ requestId }) {

// 2) ตรงที่สร้าง headers ให้เพิ่มบรรทัดนี้
if (requestId) headers["X-Request-ID"] = requestId;
```
> ถ้า `headers` ถูกสร้างอยู่ในฟังก์ชัน `request()` กลาง ไม่ได้อยู่ใน `process` ให้ส่งฟังก์ชัน `process` ทั้งก้อนมาให้ผมดูครับ จะได้ไม่แก้ผิดที่ อีกเรื่องที่ต้องเช็กคือชื่อ key ของ token ใน `localStorage` ต้องตรงกับ `authHeader()` ใน `eta.js` ด้วย

### `[FE-80]` `proxy.py`: เช็ก 2 อย่าง
- ต้อง**ส่งต่อ** header `X-Request-ID` ไปให้ backend และ**ห้ามสร้างค่าใหม่ทับ** (`Ctrl+F` ค้นหา `request-id` ถ้าเจอโค้ดที่ตั้งค่านี้เอง ให้แก้เป็นใช้ค่าของ client ก่อน)
- `GET /api/v1/queue/...` ต้องถูกส่งต่อเหมือน `/api/*` ตัวอื่น (ถ้า proxy ส่งต่อทุก path ใต้ `/api/` อยู่แล้ว ก็ไม่ต้องแก้)

### 🧪 ทดสอบหน้าตาแถบคิวก่อน backend พร้อม
1. ตั้ง `QUEUE_ENABLED = true` ไว้ชั่วคราว แล้วกด `Ctrl+Shift+R`
2. เปิดแท็บ **GenImage** แล้ววางโค้ดนี้ใน Console เพื่อจำลองคิว:
```js
(() => { const real = window.fetch; let n = 4;
  window.fetch = (url, opt) => String(url).includes("/api/v1/queue/")
    ? Promise.resolve(new Response(JSON.stringify(
        n > 0 ? { state: "queued", position: n--, total: 5 }
              : { state: "processing", avg_process_sec: 60 }),
        { headers: { "Content-Type": "application/json" } }))
    : real(url, opt);
})();
```
3. กดปุ่มส้ม ปุ่มต้องขึ้น `อยู่คิวที่ 4 จาก 5` แล้วนับลงเป็น 3, 2, 1 จากนั้นเปลี่ยนเป็น `เหลือ ~1 นาที`
4. กด `F5` เพื่อล้างการจำลอง แล้วตั้ง `QUEUE_ENABLED` กลับเป็น `false`

# ส่วนที่ 3: คำขอถึงปั้น (Backend)

## 📨 ระบบคิว: สิ่งที่ frontend ต้องได้รับ

**[BE-17] รับ header `X-Request-ID` จากทุกคำขอประมวลผลภาพ**
frontend จะสร้างรหัสนี้เองแล้วแนบมากับ `POST /api/v1/{adjust, filter, blur, remove-background, generate}` ทุกครั้ง backend ต้องใช้รหัสนี้ลงทะเบียนคิว**ทันทีที่ได้รับคำขอ** และห้ามสร้างรหัสใหม่ทับ

**[BE-18] เพิ่ม endpoint ดูสถานะคิว**
```
GET /api/v1/queue/{request_id}
Authorization: Bearer <token>
```
ตอบกลับ:
```json
{
  "request_id": "a1b2c3...",
  "state": "queued",
  "position": 3,
  "total": 5,
  "avg_process_sec": 4.2
}
```
| ฟิลด์ | ความหมาย |
|---|---|
| `state` | `queued` (รอคิว) / `processing` (กำลังทำ) / `done` / `failed` |
| `position` | ลำดับของคำขอนี้ โดย **1 = คิวถัดไป** ส่งมาเฉพาะตอนเป็น `queued` |
| `total` | จำนวนงานที่รออยู่ทั้งหมด (ไม่บังคับ) |
| `avg_process_sec` | ค่ามัธยฐานของเวลาประมวลผล**จริง**ของเครื่องมือนี้ เช่น 20 ครั้งล่าสุดของผู้ใช้ทุกคน ไม่รวมเวลารอคิว (ไม่บังคับ แต่แนะนำ เพราะทำให้เวลาที่แสดงแม่นขึ้นมาก) |

- ถ้ายังไม่รู้จักรหัสนี้ ให้ตอบ **404** frontend จะลองถามซ้ำเองอีกไม่กี่ครั้ง
- error ต้องใช้รูปแบบ `{"error":{"code","message","request_id"}}` เหมือนเดิม
- **ความเป็นส่วนตัว:** ต้องตอบเฉพาะคำขอของเจ้าของ token เท่านั้น ห้ามเปิดดูคำขอของคนอื่นได้

**[BE-19] 🔴 เวลารอคิวต้องนับรวมอยู่ใน timeout เดิม**
เวลาที่ frontend รอได้ทั้งหมดคือ **330 วินาที นับตั้งแต่กดปุ่ม** ซึ่งรวมทั้งเวลารอคิวและเวลาประมวลผล ถ้าคิวยาว คำขอจะหมดเวลาไปทั้งที่ยังไม่ได้ประมวลผลเลย
**ขอให้:** ถ้าคาดว่าเวลารอคิวรวมกับเวลาประมวลผลจะเกิน **300 วินาที** ให้ปฏิเสธตั้งแต่ตอนรับคำขอ ด้วย `503 {"error":{"code":"QUEUE_FULL","message":"ระบบมีผู้ใช้งานจำนวนมาก กรุณาลองใหม่ภายหลัง"}}`

**[BE-20] เอางานออกจากคิวเมื่อผู้ใช้ยกเลิก**
ถ้าผู้ใช้กดยกเลิก ปิดหน้าเว็บ หรือคำขอหมดเวลา การเชื่อมต่อจะถูกตัด backend ต้องเอางานนั้นออกจากคิว ไม่งั้น AI จะเสียเวลาประมวลผลงานที่ไม่มีใครรอแล้ว และทำให้คิวของคนอื่นยาวขึ้น

**คำถามที่ต้องตอบก่อนเริ่มทำ**
| รหัส | คำถาม |
|---|---|
| BE-21 | ใช้คิวเดียวรวมทุกเครื่องมือ หรือแยกคิวตามเครื่องมือ (ถ้ามีคนรอสร้างภาพ AI อยู่ คนที่จะใช้ปรับภาพต้องรอด้วยไหม) |
| BE-22 | ประมวลผลพร้อมกันได้กี่งาน (1 งาน หรือหลายงานพร้อมกัน) |
| BE-23 | ระบบคิวอยู่ใน backend หรือใน AI_server (ถ้าอยู่ใน AI_server ต้องดึงแก้วเข้ามาคุยด้วย) |
| BE-24 | ตอนเริ่มเปิดใช้ endpoint คิว ขอให้แจ้ง frontend ด้วย เพื่อเปลี่ยน `QUEUE_ENABLED` เป็น `true` |

## 📨 ถึงแก้ว
- **[AI-14] (ยังค้างอยู่)** ขอเวลาประมวลผลจริงของแต่ละเครื่องมือบนเครื่องที่จะใช้เดโม เพื่อนำไปแทนค่าเริ่มต้นที่ตอนนี้ยังเป็นค่าที่ตั้งเอง
